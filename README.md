# RI-Project — IntelliBot / IntelliWarehouse

A software-only simulation (Webots + Python) of a miniature warehouse robot
performing an autonomous pick-and-deliver mission:

> **"Pick package P3 (blue) and deliver it to Zone B (cyan)."**

Pipeline: find package (front/rear cameras) → plan route (A*) → navigate
(PID waypoint following) → avoid obstacles (LiDAR safety stop, re-planning)
→ **dock and pick the parcel with the robot arm** → re-plan → **dock at the
destination rack and place the parcel on a shelf slot** → verify → mission
report. The robot *perceives, decides, plans, and controls in a closed loop*
— no hard-coded routes.

> **Final-evaluation additions (branch `feature/ankit-arm-shelves-camera`):**
> shoulder/elbow/wrist arm with a parallel gripper and a Webots `Connector`
> latch, destination racks behind zones A/B, a docking controller, fixed
> front/rear cameras, and the matching FSM states. Implemented and tested
> offline; **the Webots runs are still pending** — see
> [Arm, shelves and cameras](#arm-shelves-and-cameras) and
> `docs/implementation_plan_ankit.md`.

## Repository layout

```
worlds/warehouse.wbt                  # GENERATED by tools/generate_world.py
controllers/intellibot_controller/    # main controller (folder name == entry file name)
    intellibot_controller.py          #   entry point: main loop, wires modules
    config.py                         #   ALL constants, layout, device names
    kinematics.py pid.py              #   pure: diff-drive kinematics, PID
    mapping.py a_star.py path_utils.py#   pure: grid, planner, post-processing
    warehouse_grid.py                 #   pure: real warehouse grid from config
    detector.py estimation.py         #   pure: HSV detection, pixel→world
    waypoint_follower.py decision_maker.py #   pure: waypoint follower, FSM
    arm_kinematics.py arm_controller.py   #   pure: arm FK/IK + clearance, joint/Cartesian motion
    gripper.py pick_place.py          #   pure: gripper + latch + grasp checks, pick/place steps
    docking.py shelving.py            #   pure: fine positioning, racks/slots/dock lines
    camera_pipeline.py                #   pure: BGRA->BGR, frame health, camera R
    perception.py arm_driver.py       #   Webots device wrappers (sensors/cameras, arm)
    logger.py                         #   CSV logging
controllers/manip_check/              # arm / gripper / camera validation controller
controllers/drive_test/               # scripted motion + validation controller
tools/                                # world generator + offline analysis
tests/                                # pytest suite (pure modules)
docs/                                 # architecture, findings, evidence, QA prep
logs/                                 # CSVs from simulation runs
```

Design rule: everything that doesn't need the simulator is pure Python
(tested with pytest); only `intellibot_controller.py`, `perception.py`,
`arm_driver.py` and the test controllers (`drive_test`, `manip_check`) touch
the Webots API.

## Requirements

- **Webots** R2023b or newer (developed against R2025a file format)
- **Python 3.9+** with `numpy`, `opencv-python`, `matplotlib`, `pytest`

```bash
pip install -r requirements.txt
```

In Webots: *Tools → Preferences → General → Python command* must point to the
interpreter that has these packages (on Windows the full path to
`python.exe`).

## Regenerate the world

The world is generated from `config.py` so the simulator and the planner's
map can never disagree:

```bash
python tools/generate_world.py        # writes worlds/warehouse*.wbt (+ copies in worlds_output/)
python tools/validate_world.py        # static checks: node types, devices, camera FOV, determinism
```

The three v1 worlds are identical except for the robot's controller:
`warehouse.wbt` runs `intellibot_controller` (mission),
`warehouse_drive_test.wbt` runs `drive_test` (Phase 2/3 validation),
`warehouse_manip_check.wbt` runs `manip_check` (arm / gripper / cameras).
Never edit a `.wbt` by hand — change `config.py` and regenerate (a test fails
if a world on disk differs from the generator).

## Run the mission demo

```bash
webots worlds/warehouse.wbt           # or open the file in Webots and press ▶
```

Watch the console: FSM transitions print as
`[FSM] [t=12.3s] STATE: NAVIGATE -> PICK`, A* stats print per plan, and the
run ends with `MISSION REPORT: time=..., path_length=..., replans=0,
collisions=N/A`. At PICK the robot lifts P3 onto its back (Supervisor
teleport) and sets it down inside Zone B at DONE. An interactive run then
idles with the dashboard live; with `RUN_INDEX` set, `AUTO_QUIT=True`
(config.py) ends the simulation at DONE/ERROR. The run log is written to
`logs/run.csv`.

If Webots' Python command is set correctly the controller starts silently;
`ModuleNotFoundError: cv2/numpy` means Preferences points at the wrong
interpreter.

## Run the validation controllers (drive_test)

Use the `warehouse_drive_test.wbt` world and pick the mode with an
environment variable (Git Bash shown; webots.exe lives in
`<Webots>/msys64/mingw64/bin/`). Outputs go to the repo-root `logs/` and
`docs/evidence/`:

```bash
W="webots --batch --mode=fast --stdout --stderr --minimize worlds/warehouse_drive_test.wbt"
DRIVE_TEST_MODE=worldcheck  $W   # Phase 2.3: "[WORLD CHECK] world matches config"
DRIVE_TEST_MODE=stability   $W   # Phase 3.1: 10 s at rest -> logs/stability.csv
DRIVE_TEST_MODE=sequence    $W   # Phase 3.2: forward/spin/arc/reverse, prints pose
DRIVE_TEST_MODE=kinematics  $W   # Phase 3.3: -> logs/kinematics_test.csv
DRIVE_TEST_MODE=odometry    $W   # Phase 3.4: -> logs/odometry.csv
DRIVE_TEST_MODE=snapshot webots --batch --mode=realtime --stdout --stderr worlds/warehouse_drive_test.wbt
                                 # Phase 2.2: world_topdown.png / world_angle.png (needs rendering)
DRIVE_TEST_MODE=capture     $W   # Phase 4.7: spin frames -> docs/evidence/frames/spin_*.png
DRIVE_TEST_MODE=capture_set $W   # Phase 4.7/4.10: 108-frame eval set (dist x angle x lighting)
                                 #   with Recognition ground truth -> frames/set/ + index CSV
DRIVE_TEST_MODE=lidar       $W   # Phase 4.2/4.4: raw scans -> logs/lidar_raw.csv
python tools/calibrate_lidar.py  # ray order + range table -> lidar_validation.md + lidar_scan.png
python tools/analyze_logs.py     # tables + odometry_vs_gps.png + kinematics_validation.md
```

Opening the world from the Webots GUI runs `sequence` (the default mode).

## Repeatability campaign (checklist 6.8)

`config.CAMPAIGN_STARTS` holds 10 start poses. Run the mission once per
index — the supervisor teleports the robot to that pose at startup and the
log goes to `logs/run_<i>.csv`:

```bash
RUN_INDEX=0 webots worlds/warehouse.wbt   # ... up to RUN_INDEX=9
python tools/analyze_logs.py              # -> docs/evidence/runs_summary.md
```

(If your shell doesn't propagate the variable to Webots, temporarily set it
inside `intellibot_controller.py`'s `apply_campaign_start`.)

## Detector evaluation set (capture in simulation)

1. Run the world; during FIND_PACKAGE press the Webots screenshot button or
   add temporary `camera.saveImage()` calls (see `perception.get_frame`).
2. Save ≥30 frames per package at 0.5–3 m, several angles, 3 lighting levels
   into `docs/evidence/frames/`.
3. Write `docs/evidence/frames/ground_truth.csv`:
   `frame,pkg,present` (e.g. `f001.png,P3,1`).
4. `python tools/eval_detector.py`.

## Arm, shelves and cameras

### What is in the world now
* **Arm** on a post at the back of the robot: shoulder, elbow, wrist
  (`shoulder_motor`/`elbow_motor`/`wrist_motor` + `*_sensor`), two fingers
  (`finger_left_motor`/`finger_right_motor`, force pads `finger_*_touch`),
  palm range-finder `palm_range`, latch `gripper_latch` (active `Connector`).
  Every parcel has a passive `Connector` on each vertical face.
* **Destination racks** `DEST_RACK_A` / `DEST_RACK_B` against the east wall
  behind the zones; slots `RA|RB-L1|L2-B1|B2` (level 3 is out of the arm's reach).
* **Cameras** `camera` (front) and `rear_camera` (rear, rotated π): planar,
  1.0 rad, 320×240, lenses 0.12 m high on the front/back faces.

### Run the pick-and-place mission
```bash
webots worlds/warehouse.wbt                # GUI: the task dialog appears (interactive mode)
# batch, no dialog (Git Bash / Linux):
INTELLIBOT_TASK_PACKAGE=P3 INTELLIBOT_TASK_ZONE=B INTELLIBOT_INTERACTIVE=0 \
    webots --batch --mode=fast --stdout --stderr worlds/warehouse.wbt
python tools/run_scenario.py S1_store_P3_B --runs 10      # same, 10 runs -> logs/final/
```
Console: `STATE: NAVIGATE -> DOCK_PICK`, `[DOCK_PICK] DOCKED: range …`,
`[MANIP] CHECK_GRASP: OK width=20.0cm …`, `STATE: … -> VERIFY_DELIVERY`,
`MANIPULATION: result=DELIVERED, slot=RB-L1-B1 …` and an `[AUDIT]` line
(Supervisor ground truth, evaluation only). Files: `logs/run.csv`,
`logs/manip.csv`, `logs/mission_report.json`. Then:
```bash
python tools/analyze_manipulation.py      # -> docs/evidence/manipulation_results.md
python tools/plot_manipulation.py         # -> docs/evidence/manip_timeline.png
```

## Navigation, localisation and safety (EKF + dynamic replanning + speed governor)

The robot now drives with the EKF pose (`localization.py`: signed encoder
increments, GPS + IMU with health-scaled R, kidnapped-robot relocalisation),
fuses the LiDAR continuously into the dynamic layer of the grid
(`dynamic_map.py`), replans with A* **from its current pose** when the route is
blocked, it is displaced, it deviates, it is stuck or it bumps into something
(`decision_maker.py`), and every command passes the speed governor
(`safety.py`, cruise 0.45 m/s, stopping-distance limited). Details, root
causes and offline numbers: `docs/ankit_implementation_report.md`.

```bash
python -m pytest tests/ -q                         # 303 tests, no Webots
python tools/offline_mission_sim.py                # one kinematic mission (full stack)
python tools/run_experiments.py                    # ablation matrix -> docs/evidence/experiments/
python tools/run_scenario.py --list                # Webots scenarios incl. A_* ablations
```

Ablation switches (config or environment): `INTELLIBOT_LOC_MODE=ekf|odom|gps`,
`INTELLIBOT_GOVERNOR=0|1`, `INTELLIBOT_DYN_REPLAN=0|1`.

## Known limitations (honest list)

- Measured in Webots so far: world/config consistency, rest stability,
  kinematics (v, ω within 0.9 %), odometry drift, one full FSM mission run
  (FIND→…→DONE, 181 s) and detector detection rate on a 13-frame spin
  sample. Still **pending measurement**: LiDAR ray-order calibration and
  range accuracy, LiDAR-fused position error, lighting variants, the
  ≥10-run success campaign, screen recording. See `docs/webots_findings.md`
  and `docs/evidence/inventory.md`.
- First full mission run (2026-10-06) reached DONE in 61.7 s sim time, but
  the package position estimate was ~0.6 m short (LiDAR ray order still
  unverified, Phase 4.2). Pickup is still a placeholder.
- Localization = EKF over wheel odometry + GPS + IMU (the Webots GPS is
  noise-free, so the EKF mostly tracks it there); no LiDAR map matching / SLAM.
- Pickup was a placeholder in the mid-eval. The final-eval arm/latch pickup
  is implemented and tested offline only (kinematic simulator + unit tests);
  physical behaviour in Webots (grip stability, docking accuracy, success
  rate) is still to be measured. Retrieve missions (shelf → zone) are not
  implemented. Racks are reached only at levels 1–2.
- The arm post creates a ~13° LiDAR blind sector straight behind the robot
  (self-filtered); reversing relies on the remaining rear rays and the rear
  bumper.
- Dynamic replanning, the EKF navigation pose and the speed governor are
  wired live (branch `fix/ankit-ekf-navigation-manipulation`) but verified
  **offline only** so far — see `docs/ankit_implementation_report.md` §10 for
  the Webots checks still to do.
