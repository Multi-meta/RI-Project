# RI-Project — IntelliBot / IntelliWarehouse

A software-only simulation (Webots + Python) of a miniature warehouse robot
performing an autonomous pick-and-deliver mission:

> **"Pick package P3 (blue) and deliver it to Zone B (cyan)."**

Pipeline: find package (camera) → plan route (A*) → navigate (PID waypoint
following) → avoid obstacles (LiDAR safety stop) → pick (placeholder in
mid-eval) → re-plan → deliver → mission report. The robot *perceives,
decides, plans, and controls in a closed loop* — no hard-coded routes.

## Repository layout

```
worlds/warehouse.wbt                  # GENERATED by tools/generate_world.py
controllers/intellibot_controller/    # main controller (folder name == entry file name)
    intellibot_controller.py          #   entry point: main loop, wires modules
    config.py                         #   ALL constants, layout, device names
    kinematics.py pid.py              #   pure: diff-drive kinematics, PID
    mapping.py a_star.py path_utils.py#   pure: grid, planner, post-processing
    warehouse_grid.py                 #   pure: real warehouse grid from config
    detector.py estimation.py         #   pure: HSV detection, pixel→world
    controller.py decision_maker.py   #   pure: waypoint follower, FSM
    perception.py                     #   Webots device wrappers
    logger.py                         #   CSV logging
controllers/drive_test/               # scripted motion + validation controller
tools/                                # world generator + offline analysis
tests/                                # pytest suite (pure modules)
docs/                                 # architecture, findings, evidence, QA prep
logs/                                 # CSVs from simulation runs
```

Design rule: everything that doesn't need the simulator is pure Python
(tested with pytest); only `intellibot_controller.py`, `perception.py` and
`drive_test.py` touch the Webots API.

## Requirements

- **Webots** R2023b or newer (developed against R2025a file format)
- **Python 3.9+** with `numpy`, `opencv-python`, `matplotlib`, `pytest`

```bash
pip install -r requirements.txt
```

In Webots: *Tools → Preferences → General → Python command* must point to the
interpreter that has these packages (on Windows the full path to
`python.exe`).

## Regenerate the world

The world is generated from `config.py` so the simulator and the planner's
map can never disagree:

```bash
python tools/generate_world.py        # writes worlds/warehouse.wbt
```

## Run the mission demo

```bash
webots worlds/warehouse.wbt           # or open the file in Webots and press ▶
```

Watch the console: FSM transitions print as
`[FSM] [t=12.3s] STATE: NAVIGATE -> PICK`, A* stats print per plan, and the
run ends with `MISSION REPORT: time=..., path_length=..., replans=0,
collisions=N/A`. `AUTO_QUIT=True` (config.py) ends the simulation at
DONE/ERROR. The run log is written to `logs/run.csv`.

If Webots' Python command is set correctly the controller starts silently;
`ModuleNotFoundError: cv2/numpy` means Preferences points at the wrong
interpreter.

## Run the validation controllers (drive_test)

Set the mode via environment variable before starting Webots (or edit the
default in `drive_test.py`):

```bash
DRIVE_TEST_MODE=sequence    webots worlds/warehouse.wbt   # scripted motions
DRIVE_TEST_MODE=kinematics  webots worlds/warehouse.wbt   # logs/kinematics_test.csv
DRIVE_TEST_MODE=odometry    webots worlds/warehouse.wbt   # logs/odometry.csv
```

Note: to change the mode you can also temporarily edit
`controllers/drive_test/drive_test.py` (`os.environ.get("DRIVE_TEST_MODE",
"sequence")`) if your shell doesn't propagate the variable to Webots.

## Run tests (no Webots needed)

```bash
python -m pytest tests/ -q            # 63 tests, ~1 s
```

## Offline evidence tools

```bash
python tools/plot_astar.py            # docs/evidence/astar_pickup_to_zoneB.png + A*/Dijkstra check
python tools/analyze_logs.py          # metrics.md + odometry overlay (after runs)
python tools/plot_lidar.py            # lidar_scan.png (after logs/lidar_scan.csv exists)
python tools/eval_detector.py         # detector_eval.md (after frame capture)
```

## Detector evaluation set (capture in simulation)

1. Run the world; during FIND_PACKAGE press the Webots screenshot button or
   add temporary `camera.saveImage()` calls (see `perception.get_frame`).
2. Save ≥30 frames per package at 0.5–3 m, several angles, 3 lighting levels
   into `docs/evidence/frames/`.
3. Write `docs/evidence/frames/ground_truth.csv`:
   `frame,pkg,present` (e.g. `f001.png,P3,1`).
4. `python tools/eval_detector.py`.

## Known limitations (honest list)

- Webots was not runnable on the build machine — all simulator-dependent
  numbers (kinematics error, LiDAR accuracy, detector rates on REAL frames,
  cross-track error, success rate) are **pending measurement**; the tools
  above produce them from real logs. See `docs/webots_findings.md`.
- Localization uses GPS+IMU (idealized); wheel odometry is implemented and
  validated against it. A real robot needs odometry+LiDAR localization/SLAM.
- Pickup is a placeholder in the mid-eval (attach mechanism = final eval).
- Dynamic re-planning hooks exist and are unit-tested but not wired live
  (final-eval "wow" feature).
